## 2. 严重错误（高优先级，建议先修）

### 🔴 2.1 引擎释放接口契约错位，`release_engine()` 是死代码

- 位置：`core/ocr_engine.py:781-802`、`core/asr_engine.py:858`
- 问题：`release_engine` / `release_all_engines` 用 `hasattr(eng, "close")` 判断后调用 `close()`，但 **OCR/ASR 引擎类都没有定义 `close()`**（已核实：`core/ocr_engine.py` 只有 `_stop_server()`、`core/asr_engine.py` 只有 `_stop_server()`）。因此切换/释放引擎时：
  - OCR 子进程（`use_subprocess` 模式）不会被停止，共享内存不会关闭；
  - ASR 子进程不被回收；
  - `reload_config()`（`ocr_engine.py:719-721`）直接 `_engines.clear()`，配置热重载反复叠加泄漏的子进程与共享内存块。
- 复核：grep 确认所有引擎类无 `close` 方法。

### 🔴 2.2 多区域并行 OCR 对同一引擎实例并发调用 `predict()`（非线程安全）

- 位置：`core/frame_processor.py:142-201`
- 问题：`_process_regions_parallel` 用 `ThreadPoolExecutor(max_workers=4)` 对每个 region 执行 `get_engine(re_name)` 后并发 `_process_frame`。多区域共用同一引擎时（默认常见），返回的是**同一缓存实例**，`PaddleOCR.predict()` 被 4 线程并发调用。PaddleOCR 推理非线程安全，可能崩溃或返回异常结果；`self._last_confidence` 也被并发写。
- 建议：引擎实例级加锁串行化，或按引擎分桶排队。

### 🔴 2.3 OCR 子进程模式 + 多区域并发：共享内存单缓冲导致图像/响应错配

- 位置：`core/ocr_engine.py:435-459`、`core/ocr_server.py:268`、`core/subprocess_utils.py:378-387`
- 问题：
  1. 所有请求共用唯一 `SharedMemoryManager("orcp_ocr_img")`，线程 A 写入后线程 B 覆盖同一块内存，服务端读到 B 的图像给 A；
  2. 请求 `id` 恒为 0，响应队列按到达顺序弹，A 可能拿到 B 的结果；
  3. `write_array` 容量扩展时 `close+unlink` 后重建，无锁，并发下双重 unlink/create 互相覆盖。
- 建议：为每请求分配唯一 `id` 并按 id 匹配响应；子进程调用加互斥锁。

### 🔴 2.4 ASR 流式模式 Popen stderr 管道满死锁

- 位置：`core/asr_engine.py:332-363,414`
- 问题：流式转写用裸 `Popen` + `stderr=PIPE`，进入转写后父进程**从不消费 stderr**。Windows 管道缓冲仅几十 KB，子进程模型下载进度/报错堆栈写满 stderr 后阻塞 → 不再写 stdout → 父进程 `readline` 永久卡死，只能等 300s 超时 `kill`。
- 建议：`stderr=DEVNULL` 或启动 daemon 线程排空 stderr。

### 🔴 2.5 UI：置信度过滤 `removeRow` 空操作 + 直接删列表，模型/视图状态不一致

- 位置：`ui/main_window.py:1510-1511`
- 问题：`_ResultsModel`（`ui/result_table.py:79`）**未实现 `removeRows()`**，`QAbstractTableModel` 默认返回 `False`，`table.removeRow(row)` 实际为空操作；随后 `del results[row]` 直接删共享列表，模型 `rowCount()` 与视图索引错位、残留脏行，极端情况越界。
- 建议：用 `beginRemoveRows/endRemoveRows` 包裹删除，或整表 `beginResetModel`。

### 🔴 2.6 UI：程序化刷新触发视频跳帧（流式纠错持续 seek + 点击任意列跳转）

- 位置：`ui/result_table.py:471-476,748` + `ui/main_window.py:1073`
- 问题：
  1. `update_correction_result()` 发 `dataChanged` 时 `roles` 为空 → 命中 `cell_edit_activated` → 执行 `vp.seek_to(ts)`。**流式 AI 纠错逐字更新时视频持续跳帧**；
  2. `_on_cell_clicked` 对任意列（含复选框列）点击都 emit 跳转，勾选复选框也会跳视频。
- 建议：区分"编辑器提交"与"程序化更新"（如仅 `EditRole` 且来源为编辑器时跳转）。

### 🔴 2.7 UI：ASR 区域参数逐键触发引擎重建（OOM 风险）

- 位置：`ui/views/right_panel.py:175-185,303` + `ui/main_window.py:1125-1137`
- 问题：ASR 参数 `textChanged` 每次击键 → `_restart_asr_engine()` → 后台 `reload_config() + get_engine()`，**可能重新加载整份 faster-whisper 模型**。在"区域名"输入框每敲一个字就重建一次，内存反复分配/加载。
- 建议：对 ASR 参数变更加防抖（复用 `_schedule_mode_save` 的 300ms 定时器，延迟到输入停止）。

### 🔴 2.8 LLM：空 API Key 导致本地服务纠错静默失败

- 位置：`core/llm_utils/llm_client.py:313-315`
- 问题：`ask_llm()` 在 `api_key` 为空时直接 `return None`。但本地 llama.cpp/Ollama 服务器通常不需要 key（对比 `core/ocr_engine.py:56` 用 `api_key or "not-needed"`）。结果：本地无 key 服务跑 AI 纠错全部静默失败。
- 建议：`api_key = api_key or "not-needed"`（本地服务忽略 key）。

### 🔴 2.9 LLM：损坏的缓存文件让该 `log_title` 所有后续请求失败并浪费 7 秒重试

- 位置：`core/llm_utils/llm_client.py:85-98`
- 问题：缓存读取只捕获 `json.JSONDecodeError, OSError`。若缓存文件是**合法 JSON 但顶层不是 list**（被手工编辑或 `{}`/`null`），迭代后 `entry.get` 抛 `AttributeError/TypeError` → 被 `@except_handler` 当成 API 失败重试 3 次（睡 1+2+4=7 秒）后返回 `None`。
- 建议：加 `isinstance(entry, dict)` 校验。

### 🔴 2.10 脚本 `scripts/run_ocr.py` 与 PaddleOCR 3.x 不兼容

- 位置：`scripts/run_ocr.py:32,157`
- 问题：直接调用 `PaddleOCR(use_angle_cls=True, ...)`。PaddleOCR 3.x 已移除 `use_angle_cls`（改名 `use_textline_orientation`），传入会抛 `TypeError`；且按 2.x 返回结构 `results[0]` 解析，与 3.x 不兼容。主代码 `core/ocr_server.py:234-238` 专门做了参数映射，反证此脚本已过时。
- 建议：删除或迁移该脚本到 3.x API。

### 🔴 2.11 日志格式化器污染共享 record，日志文件写入 ANSI 转义码

- 位置：`core/logger.py:54-66`
- 问题：`_ColoredFormatter.format()` 将 `record.levelname` **就地改写**为带 ANSI 码的字符串且从不恢复。`logging` 所有 handler 共享同一 `record`，控制台 handler 先运行污染后，文件 handler 写出的 `logs/orcp.log` 每行级别字段都含 `\x1b[...]m`，破坏 grep/日志工具解析。
- 建议：格式化前先恢复 `record.levelname`（在 finally 中还原）。

### 🔴 2.12 重复脚本 `scripts/img tools.py` 与 `scripts/img_tools.py`

- 位置：`scripts/img tools.py`、`scripts/img_tools.py`
- 问题：SHA256 **完全一致**（`FC5198...`，82,906 字节 / 2092 行），均被 git 跟踪，全仓无引用。带空格的文件名影响 CLI 使用；后续修改会只改其中一个造成漂移。
- 建议：删除其中一个，并让保留版本复用 `core/config_manager` 的 JSON 解析器。

### 🔴 2.13 `download_gpu.py` 安装无版本约束 torch，绕过 `<2.11` 锁定

- 位置：`scripts/download_gpu.py:32-33`
- 问题：`uv pip install torch torchvision torchaudio --index-url ...` 不指定版本，可能拉取 ≥2.11 与 `pyproject.toml` 的 `torch<2.11` 冲突；`torchvision` 不在项目依赖中（额外下载数百 MB）；GPU 安装完全绕过 lock 文件。且脚本 `:39-42` 的 torch 校验分支被 `:42 ok = True` 无条件短路，安装失败仍 `exit 0`。
- 建议：对齐 `torch<2.11` 约束，删除 `torchvision`，修复退出码逻辑。
